# DevFlow RAG｜技术文档检索与智能故障诊断平台

> 项目总体设计 v1.0｜2026-11-04｜**规划文档，不代表当前代码已经实现**  
> 代码仓库：<https://github.com/X-WangPengLin/DevFlow-Ai->  
> 本文为独立原创设计；仅借鉴公开 OnCall Agent 的场景思路，不复制其源码或受限课程内容。

## 1. 项目愿景与最终成果

**一句话定位**：面向开发、运维和技术支持工程师的 **RAG 驱动技术故障诊断平台**。用户上传 Docker、Kubernetes、Nginx、Spring Boot 等技术手册、Runbook 与 FAQ，输入错误码、日志及环境信息，系统检索出相关、版本匹配的文档证据，综合可观察事实与知识依据，生成可追溯的故障假设和安全的排查建议。

**最终交付形态（L3）**：一个可在 Mac / Docker Compose 本地部署、可通过浏览器使用、具备真实文档入库与检索、故障诊断报告、引用回跳、实验对比和评测报告的完整 Web 产品。不是单纯的“上传 PDF 聊天”，也不是无人监管的自动生产运维系统。

**目标用户**：①研发工程师（排查启动、配置与依赖异常）；②运维工程师（排查容器、网络和服务可用性）；③技术支持（查询版本手册和标准处理步骤）。

**非目标**：不开发 GitHub PR/Issue 平台；不做通用多 Agent 平台；不直接连接生产服务器执行重启、删除、写配置等危险操作；不承诺自动确定所有故障根因。

## 2. 三个核心卖点

1. **技术故障专用的高质量检索**：对错误码、异常类名、命令、配置键和版本号强化精确检索；以 Dense 为起点，通过 BM25 + RRF + Rerank、结构化 Chunking 与版本过滤进行实验优化。
2. **双通道、证据驱动的故障诊断**：规则通道只提取可观察事实（如 HTTP 502、Connection refused、容器 unhealthy）；RAG 通道提供官方手册或 Runbook 的外部依据；融合层将“观察事实 / 候选原因 / 尚待验证 / 下一步检查”明确分开。
3. **可解释与可评测的 RAG**：展示检索候选、排名变化、召回来源、每段执行耗时和引用；提供固定评测集、消融实验、错误归因及检索准确率、诊断可靠性、延迟、成本对比。

## 3. 最终用户可操作的功能

### 3.1 知识库管理
- 新建知识库、导入 Markdown / PDF / DOCX（DOCX 为后续扩展）；支持文档来源、产品、版本、发布日期、章节/页码等元数据。
- 显示解析 → 切分 → 嵌入 → 索引的每个状态、失败原因和重试；保留原件与索引版本。
- 文档引用可跳转原文或定位片段；索引可按新策略重建，不覆盖原始文档。

### 3.2 技术知识问答
- 询问错误码、参数、命令或产品配置；对问题中的技术实体和版本做识别。
- 返回带原文引用的答案；证据不足时明确说明，禁止凭空补充未检索到的来源。
- 支持配置 Dense / Hybrid / Rerank 检索策略；用户不必了解底层算法也可正常使用。

### 3.3 故障诊断工作台（核心业务）
- 输入故障描述、脱敏日志、运行状态、产品与版本；只处理用户提供的观测数据，不默认连接生产环境。
- 规则通道提取事实；RAG 检索相关故障手册、Runbook；诊断引擎提出候选原因与验证步骤。
- 输出 `DiagnosisReport`：故障概述、观察事实、候选原因、支持/反对证据、需要补充的信息、建议检查步骤、引用。
- 用户补充排查结果后可重新生成报告，保留诊断案例历史。建议命令只用于人工阅读、审核后自行执行。

### 3.4 检索调试台（Retrieval Playground）
- 对同一查询显示 Dense、BM25、RRF、Rerank 各阶段 Top-K、来源、排名、得分与耗时。
- 提供文档片段对比、版本过滤和“不相关/相关”标注，辅助定位检索失败原因。

### 3.5 评测实验室（Evaluation Lab）
- 管理问题、标准证据、参考答案、可回答性、产品版本及人工审核状态。
- 执行固定配置实验，对比 Recall@K、MRR、nDCG、引用有效率、拒答行为、诊断事实准确性、P50/P95 时延和调用成本。
- 错误分类：解析、切分、漏召回、错排序、上下文丢失、生成幻觉、错误引用、版本错配、错误拒答。

## 4. 关键业务闭环

**文档入库**：文件校验 → 安全存储 → 文档结构解析 → Chunk + 来源信息 → Embedding → pgvector 入库 → 关键词索引（V0.2）→ 状态可观测。

**在线查询**：故障问题 → 技术实体/版本识别 → [Dense ∥ BM25] 召回 → RRF 融合 → Rerank → 去重、版本过滤和上下文预算 → 带来源的知识证据。

**双通道诊断**：用户日志/故障描述 → `FaultContext` → ①确定性规则事实提取；②RAG 证据检索 → `Evidence Fusion` → 形成候选根因和下一步验证步骤 → `DiagnosisReport`。**规则匹配不等于确诊；文档中的可能原因也不等于当前系统真实根因。**

## 5. 总体架构与部署

架构图详见独立文件 `DevFlow-RAG-总体架构图.png`，以及可编辑的 `DevFlow-RAG-总体架构图.mmd`。

**部署原则：模块化单体优先**。前端 Next.js + React + TypeScript；后端 Python 3.12 + FastAPI + Pydantic + uv；SQLAlchemy + Alembic；PostgreSQL + pgvector；本地文件存储（后续可升级对象存储）；异步索引 Worker 按需求演进；Embedding、Reranker、Chat LLM 通过统一适配器接入 OpenAI 兼容 API 或本地模型。LangGraph 仅在确有动态迭代检索和状态恢复需求时引入。

**推荐主要模块**：
- `knowledge`：知识库、文档、版本和索引任务。
- `ingestion`：Parser、Chunker、Embedding 和 Index Builder。
- `retrieval`：QueryProcessor、DenseRetriever、BM25Retriever、RRF、Reranker、EvidenceBuilder。
- `diagnosis`：FaultParser、RuleMatcher、EvidenceFusion、HypothesisEvaluator、ReportBuilder。
- `generation`：引用约束、答案生成、证据不足拒答。
- `evaluation`：数据集、评测器、实验运行与报告。
- `observability`：Trace、检索候选、耗时、错误归因。
- `persistence`：文档/向量/任务/案例/评测数据的存储接口。

### 5.1 关键领域对象

| 对象 | 核心字段与职责 |
|---|---|
| `Document` / `DocumentVersion` | 知识库、来源、产品、版本、哈希、解析状态 |
| `Chunk` | 内容、标题路径、页码/源偏移、文档版本、Chunk 策略版本 |
| `RetrievalHit` | `chunk_id`、来源、阶段、排名、分数、匹配元数据 |
| `FaultContext` | 技术组件、错误码、日志原文引用、观察事实、用户环境 |
| `Evidence` | 来源文档/版本/章节、原文片段、支持的事实或假设 |
| `DiagnosisReport` | 事实、候选原因、证据、未知项、人工检查步骤 |
| `ExperimentRun` | 语料/测试集/索引/模型/策略版本、指标、时延、成本 |

## 6. 数据来源和评测策略

首批语料聚焦 Docker、Kubernetes、Nginx、Spring Boot 的官方技术手册、常见错误章节及合法使用的 Runbook。记录来源 URL、取得时间、产品版本和许可；不默认重分发第三方全文。

- **M1 基线**：约 20–30 份文档、约 50 道经人工核对的问题，覆盖概念、命令、故障、无答案问题。
- **M3 完整实验**：目标约 200 道人工审核问题，区分开发集、验证集、锁定测试集；标注**稳定的文档章节/原文跨度**，不只记录会随切分变化的 Chunk ID。
- **消融实验**：Dense → BM25 → Dense+BM25+RRF → +Rerank → +版本过滤/结构化切分；最终诊断对比“仅 RAG”与“规则+RAG”，同时比较准确性、延迟与成本。
- **评估原则**：不预设优化必定提升；每次实验固定文档、索引、模型、参数和测试集版本，真实结果才能进入简历。

## 7. 安全与可信边界

- 上传文件必须限制类型/大小、隔离存储路径，防止路径穿越、恶意内容与解析资源耗尽。
- 真实日志必须脱敏；第三方文档视为不可信输入，防止 Prompt Injection。
- 检索严格按知识库访问权限过滤；API Key 仅在环境变量与服务端使用。
- 故障建议区分已观察事实、知识依据与假设；证据不足时拒绝下确定结论。
- 所有排查命令仅提供给用户参考；**V1.0 不自动运行生产环境命令**。
- 引用只能来自实际检索并进入上下文的证据，不能由模型伪造文档或页码。

## 8. 分阶段交付与验收

| 阶段 | 一次性完整交付范围 | 必须通过的验收 |
|---|---|---|
| **M0 工程基线** | Next.js、FastAPI、Docker Compose、PostgreSQL/pgvector、文档与测试基础 | 可启动、健康检查成功、迁移成功、无密钥提交 |
| **M1 基础 RAG 闭环** | Markdown/PDF 上传、解析、Chunk、Embedding、Dense 检索、真实引用回答 | 在真实样例文档上完整运行；正确定位引用；失败状态可查；50 道审核问题建立基线 |
| **M2 检索优化** | BM25、RRF、Rerank、元数据/版本过滤、Playground 与 Trace | 同题可比较不同策略；数据与耗时可复现；消融报告可导出 |
| **M3 双通道诊断** | 故障事实规则、RAG 证据融合、候选原因、验证步骤、诊断案例 | 至少若干可复现的受控故障案例；事实/假设严格区分；能正确表达证据不足 |
| **M4 质量完善** | 扩充人工评测集、错误归因、可观测性、权限与性能、部署文档 | 全链路测试、版本化实验、延迟/成本记录、可在另一台 Mac 重建 |

**本轮建议：仅把 M0+M1 作为 Codex 第一轮完整里程碑。** 先不开发规则通道、BM25/RRF/Rerank、多 Agent 或自动运维；接口为后续演进保留。

## 9. 首轮功能验收情景

1. 用户打开知识库页面，上传一篇真实 Nginx/Docker Markdown 或 PDF 技术文档。
2. 前端显示文档处理状态，数据库内能查询到 Chunk、Embedding、索引状态。
3. 用户在问答页输入“连接被拒绝如何排查”，系统执行真实 Dense Top-K 检索。
4. 返回有依据的建议、实际文档来源及页码/标题定位；没有证据时明确拒答。
5. 重启服务后原始文档、索引和查询记录仍可用。
6. pytest、前端类型检查/构建及一次真实端到端验证通过，文档中记录每项证据；Mock 与真实 API 测试明确区分。

## 11. 待确认 / 待真实验证

- Mac 目前的真实仓库内容、Git 分支状态、Node/Python/uv/Docker 版本。
- 具体 Embedding、Reranker、Chat Model 的可用性、价格与吞吐。
- 中文技术关键词 BM25 的分词实现（PostgreSQL 内建全文检索不能直接视为完整中文 BM25）。
- 结构化 PDF 的复杂度、页码定位和解析性能。
- 所有检索质量提升均需用人工标注数据与对照实验验证，**当前没有任何实测提升数字**。

---

**项目成功的判断标准**：工程师能在真实、版本明确的技术资料中找到正确依据；系统能将故障事实、可能原因和未验证假设讲清楚；开发者能通过检索 Trace 和评测实验证明系统为什么有效、怎样改进。
